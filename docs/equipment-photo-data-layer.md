# Equipment photo data layer

## Scope

The Equipment photo data layer is implemented without adding browser routes or UI. EquipmentPhoto remains a separate Equipment-owned record and composes the neutral processing, crop and R2 mechanics through an Equipment-only storage wrapper.

The public operations are:

- `uploadEquipmentPhoto`
- `setPrimaryEquipmentPhoto`
- `updateEquipmentPhotoCrop`
- `deleteEquipmentPhoto`

The caller cannot provide photo IDs, storage keys, asset IDs, primary or ordering values, derivative revisions, timestamps or Prisma operations. Every mutation uses the owning Equipment's `updatedAt` value as its concurrency token and advances it strictly after a successful logical change.

## Equipment storage namespace

Equipment photo services accept only the closed `equipment` namespace:

```text
equipment/<equipment UUID>/<asset UUID>/original.<detected extension>
equipment/<equipment UUID>/<asset UUID>/display.webp
equipment/<equipment UUID>/<asset UUID>/thumbnails/<revision UUID>.webp
```

The original key stored in EquipmentPhoto is generated by the server. The Equipment wrapper rejects Plant paths, unknown namespaces, malformed UUID paths and broader owner-level cleanup prefixes before storage access.

## Upload lifecycle

Upload validates and processes the image, generates a fresh asset and thumbnail revision, and uploads the original, display and thumbnail before taking a database lock. A short transaction then locks Equipment with `FOR NO KEY UPDATE`, rechecks `expectedUpdatedAt`, appends the photo ordering, makes the first photo primary and advances Equipment.updatedAt.

Known storage or database failures attempt cleanup only for the new upload's objects. If a database commit result is uncertain, the operation checks for the generated storage key before deciding whether cleanup is safe. An unresolved outcome retains the objects and reports the affected keys for diagnostics rather than risking deletion of a committed photo.

Archived and nonpowered Equipment use the same flow. A photo mutation does not alter archive state, power capability, energy history, tariff data, purchase, Location or EQP reference.

## Primary and crop changes

Primary selection locks Equipment and verifies ownership and the concurrency token before atomically clearing the previous primary and selecting the requested photo. Selecting the current primary is a no-op. The database partial unique index remains the final guarantee.

Crop adjustment reads the retained original privately and creates only a new square thumbnail revision. It does not change the original or full display derivative. The database switch to the new crop and revision occurs under the Equipment lock and advances Equipment.updatedAt. A failed attempt cleans only its new revision; uncertain outcomes are resolved against the active derivativeRevision where possible.

## Deletion

Deletion is database first. The transaction locks Equipment, verifies ownership and the token, validates the exact asset prefix, rejects conflicting metadata that shares the same asset folder, deletes the metadata and promotes the next photo by sortOrder, createdAt and id when required. Equipment.updatedAt advances in the same transaction.

After commit, storage cleanup is restricted to the deleted photo's exact asset prefix. It includes the original, display, legacy thumbnail and every revision thumbnail under that asset. Cleanup cannot broaden to an Equipment owner folder, another Equipment or the Plant namespace. A cleanup failure does not recreate metadata; the result reports `cleanupPending` with safe asset information for later diagnostics.

## Read boundary

The data layer provides ordered gallery metadata, primary metadata, owned-photo lookup and bounded primary references for Equipment lists. Ordinary metadata reads do not contact R2 and do not return storage keys.

The future browser delivery route can request only `display` or `thumbnail` for a known EquipmentPhoto. The service resolves the current thumbnail revision from PostgreSQL and passes the derived Equipment key to the namespace-fixed signing wrapper. Original files, arbitrary revisions, arbitrary keys and remote URLs are not exposed.

Browser routes, gallery composition, upload forms and Equipment list thumbnails remain a later checkpoint.
